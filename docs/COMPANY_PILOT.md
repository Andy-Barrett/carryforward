## Working flow

1. Sign up and create a company, or sign into an existing account and accept a matching invitation. Invitations are local copyable links; no email is sent. Owners/admins manage access; dispatchers assign and review work; technicians see assigned jobs.
2. In Library, upload a bounded TXT/text PDF, inspect the extracted pages and explicitly approve an immutable version. Set issuer, revision and equipment applicability. Upload is not approval. Scanned/encrypted/failed extraction remains visible and cannot supply approved context. New document revisions do not rewrite old confirmed reports.
3. Create a work order with customer, site, assigned scope, technician and known equipment identity. Choose approved reference versions. Enter explicit bring-along/access notes and optional verified shop/site coordinates; no geocoding service is used. The same operation is available to a restricted company integration.
4. The technician opens the assignment, reviews Briefing and the before-departure checklist, and asks about the actual approved sources. Swipe right or tap Files for job photos and approved attached sources. Tap a file for a large preview; return to keep one compact selected-file card beside the conversation. More contains the typed fallback, local work export and sync. Original photos remain hash-checked. No image establishes safety or completed work.
5. Report findings, correct testimony and prepare the exact report. The correction dialog retains the earlier source and starts from the complete original testimony. Explicit form ownership is appended to each unresolved, ownerless branch in the same transaction as the candidate; a failed candidate rolls back that ownership change. A name on a form is not enough to confirm another user's report: the server also binds its authenticated author ID.
6. Confirm that exact revision, then separately send it. In Office inbox, a reviewer records receipt and acceptance. Accepted-with-follow-ups is a completed reporting handoff with unresolved physical/office work still owned. These local office operations do not send anything to Perihelion or a customer's system.

The fallback report form retains its in-progress fields in the same encrypted company/user/job cache as the conversation. Report preparation, confirmation, delivery and acceptance remain separate actions. A change to the assignment, report or admitted evidence invalidates the earlier confirmation rather than silently carrying it forward.

## Offline and reminders

An online authenticated session receives a fifteen-minute cache lease. Company/user/job-associated AES-GCM ciphertext is retained on logout; its key is held only by the unlocked page. Sign-out clears identity, field content, dialogs and playback immediately. A durable non-secret pending-logout marker prevents a failed/offline sign-out from silently reopening the surviving server cookie on relaunch. Admitted old-account writes drain with their original key; later callbacks cannot use a new account's cache. Cold-offline unlock and cross-account offline login are unsupported. Revocation is not a remote wipe of a disconnected device.

Only static code belongs in the worker cache. API responses, original documents and evidence are excluded. Shell updates wait for existing candidate windows to close; preserve work and close/reopen those windows after an update. Do not clear device/browser storage to force an update. Reconnect and reauthenticate when a lease or permission changes.

Optional native notifications support one active visit with explicit packing acknowledgments and manual Ready to leave / Finish visit fallbacks. Notification taps ignore event-supplied identity and revalidate the signed session, current assignment and status before opening a check. No automatic microphone, transmission, confirmation or closure occurs. Simulated shop exit delivered an actual iOS banner and acknowledgment removed the obsolete reminder.
